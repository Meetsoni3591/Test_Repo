# Test Cases for T1.1.2 - Venues Metrics

Okay, here are two detailed test cases based on the "Venues Metrics" task description.  These cover two distinct areas outlined in the description and demonstrate a good balance of functionality coverage.

**Test Case 1**

*   **Title:** Verify Total Signed Venues Metric Accuracy

*   **Description:** This test case verifies that the "Total Signed Venues" metric displayed in the Venues Metrics dashboard is accurately reflecting the total number of venues that have signed up and onboarded successfully.

*   **Steps:**

    1.  **Precondition:** Ensure a valid administrative user account exists with access to the Venues Metrics dashboard.
    2.  **Precondition:** Identify the initial "Total Signed Venues" count as displayed on the dashboard.  Record this value. (e.g., Total Signed Venues = 150)
    3.  **Navigate:** Log in to the application using the administrative user account.
    4.  **Navigate:** Access the Venues Metrics dashboard.
    5.  **Action:** Onboard a new venue (e.g., "Test Venue 1") using the standard venue onboarding process. Ensure all required information is provided and the venue is successfully activated.
    6.  **Action:** Navigate back to the Venues Metrics dashboard.
    7.  **Action:** Onboard another new venue (e.g., "Test Venue 2") using the standard venue onboarding process. Ensure all required information is provided and the venue is successfully activated.
    8.  **Action:** Navigate back to the Venues Metrics dashboard.
    9.  **Action:** Deactivate an existing active venue (e.g., "Venue XYZ") using the standard venue deactivation process.
    10. **Verify:**  Compare the "Total Signed Venues" count displayed on the dashboard with the expected value. Expected Value = Initial Value + 2 (new venues) - 1(deactivated venue) = 150 + 2 -1 = 151

*   **Expected Result:** The "Total Signed Venues" metric on the Venues Metrics dashboard should be updated to accurately reflect the current total number of signed and onboarded venues, after the addition and deactivation of the test venue. In our example, it should read 151.

*   **Priority:** High (P1) - This metric is fundamental for understanding venue growth and overall platform usage. Inaccurate data here renders other insights unreliable.

**Test Case 2**

*   **Title:** Verify Guestlist Engagement Metrics Accuracy for a Specific Venue

*   **Description:** This test case verifies that the Guestlist Engagement metrics (e.g., total RSVPs, check-ins, no-shows) displayed for a specific venue on the Venues Metrics dashboard are accurate based on actual guestlist activity.

*   **Steps:**

    1.  **Precondition:** Ensure a valid administrative user account exists with access to the Venues Metrics dashboard.
    2.  **Precondition:** Select a specific venue (e.g., "Venue Alpha") that has an active guestlist. Note its Venue ID.
    3.  **Precondition:** Note the initial Guestlist Engagement metrics for Venue Alpha (Total RSVPs = 50, Total Check-ins = 40, Total No-Shows = 5) by accessing the dashboard.
    4.  **Action:** Create a new guestlist for Venue Alpha.
    5.  **Action:** Add 5 guests to the guestlist.
    6.  **Action:** Simulate guest actions:
        *   Manually mark 3 guests as "RSVP" for the created guestlist.
        *   Manually check-in 2 of the 3 "RSVP" guests.
        *   Leave 1 guest unchecked-in, which will be counted as a "No-Show" once the guestlist event time has passed.
    7.  **Navigate:** Access the Venues Metrics dashboard.
    8.  **Filter/Select:**  Filter the dashboard to display metrics specifically for "Venue Alpha" (using Venue ID or name).
    9.  **Verify:** Compare the updated Guestlist Engagement metrics displayed on the dashboard with the expected values.

*   **Expected Result:**
    *   Total RSVPs: Should increase by 3 (Initial 50 + 3 new RSVPs = 53)
    *   Total Check-ins: Should increase by 2 (Initial 40 + 2 new Check-ins = 42)
    *   Total No-Shows: Should increase by 1 (Initial 5 + 1 new No-Show = 6)
    *   The Guestlist Engagement metrics for Venue Alpha displayed on the dashboard should accurately reflect these updated values.

*   **Priority:** High (P1) - Guestlist Engagement metrics are crucial for understanding venue popularity and marketing effectiveness.  Inaccuracies can lead to flawed business decisions.

**Important Considerations and potential follow-up test cases:**

*   **Data Aggregation Period:** These tests assume a near real-time update.  Test cases should also be created to verify the accuracy of metrics aggregated over different periods (e.g., daily, weekly, monthly).
*   **Error Handling:** What happens if there's a database error during the calculation of these metrics? A test case should cover error handling and reporting.
*   **Data Source Validation:** Validate that the metrics displayed on the dashboard are sourced from the correct tables/databases.
*   **Performance:** Test cases should be created to assess the performance of the dashboard, especially when dealing with a large number of venues and guestlist entries.  Does the dashboard load quickly?  Are the calculations efficient?
*   **Boundary Cases:**  Test extreme scenarios like having no signed venues, venues with extremely large guestlists, etc.
*   **Concurrency:** What happens if multiple users are onboarding venues or updating guestlists simultaneously? Test for race conditions.
*   **Negative Testing:** Test with invalid data.  For example, try to onboard a venue with missing required fields or corrupted data.
*   **Localization:** If the application supports multiple languages, the test cases should include steps to verify the correct display of metrics in different locales.
*   **Security:** Ensure only authorized users can access the Venues Metrics dashboard.
*   **Integration with other systems:** Ensure the metrics are consistent with any other reporting or analytics systems.
* **Data Reconciliation:** Create test cases to reconcile data between the dashboard and the underlying database to ensure no data is lost or corrupted during the aggregation process.
* **Data latency:** Ensure the latency between an event occurring and the corresponding change in the metrics is within acceptable limits.

These two test cases provide a solid foundation for testing the Venues Metrics functionality. Remember to adapt and expand upon them based on the specific requirements and complexity of your application.
