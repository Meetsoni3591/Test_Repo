# Test Cases for T1.1 - KPIs and Metrics

Okay, here are two detailed test cases based on the provided "KPIs and Metrics" task.  I've focused on two different, but critical, aspects: Data Accuracy and Data Display.

**Test Case 1: KPI Data Accuracy - User Count Validation**

*   **Title:** User Count KPI Accuracy Validation

*   **Description:** This test case verifies the accuracy of the User Count KPI displayed on the dashboard or reporting system. It ensures that the reported user count accurately reflects the actual number of users registered in the system. This test case focuses on verifying the fundamental data integrity of the User count KPI.

*   **Steps:**

    1.  **Preparation:**
        *   Establish a known User Count Baseline.  This could involve:
            *   **Scenario A: New System:** If it's a new system, note the initial user count (likely 0).
            *   **Scenario B: Existing System:** If it's an existing system, query the database directly using an SQL query (e.g., `SELECT COUNT(*) FROM Users;`) to determine the current, *authoritative* user count.  Record this baseline count.
    2.  **User Registration:**
        *   Create a number of new users using the standard user registration process (e.g., via the website, API, or administrative interface). The number of users to create depends on the overall scale of the system and the granularity needed for the KPI.  A good starting point is to create 10 new users. Record the exact number of new users created.
    3.  **Verify Database Count:**
        *   Execute the same SQL query from step 1 (e.g., `SELECT COUNT(*) FROM Users;`) to retrieve the updated user count directly from the database.
        *   Calculate the expected user count: `Expected Count = Baseline Count + Number of New Users Created`.
        *   Compare the actual database count to the calculated expected count.  The database count *must* match the expected count. If not, stop and report the error.
    4.  **Navigate to KPI Dashboard:**
        *   Log in to the reporting/dashboard system using appropriate credentials (e.g., an administrator account).
        *   Navigate to the section of the dashboard or report that displays the User Count KPI.
    5.  **Retrieve Dashboard KPI Value:**
        *   Record the User Count value displayed on the dashboard.
    6.  **Compare KPI Value to Database Count:**
        *   Compare the User Count KPI value displayed on the dashboard to the updated user count retrieved directly from the database in Step 3.

*   **Expected Result:** The User Count KPI displayed on the dashboard must exactly match the updated user count retrieved directly from the database after new users are registered. The SQL query result from Step 3 should match the value displayed on the KPI dashboard in Step 5.

*   **Priority:** High (Data accuracy is critical for trust in the entire system.)

**Test Case 2: KPI Display - User Count KPI Trend Over Time**

*   **Title:** User Count KPI Trend Graph Display Validation

*   **Description:**  This test case validates the correct display and functionality of the User Count KPI's trend graph over time. This includes checking the accuracy of data points plotted, the proper rendering of the graph, and the ability to filter the data by specific time periods. This is not only about having the number correct, but how the change to the number is displayed.

*   **Steps:**

    1.  **Preparation:**
        *   Establish a User Count History. Gather data for the User Count over a specified period (e.g., the last 7 days, the last month). This data can be retrieved from a database, a historical reporting table, or potentially from previous test runs. Record this historical data. Include at least 5 data points across your test time frame.
    2.  **Navigate to KPI Dashboard:**
        *   Log in to the reporting/dashboard system using appropriate credentials.
        *   Navigate to the section of the dashboard or report that displays the User Count KPI and its trend graph.
    3.  **Initial Graph Display:**
        *   Observe the default time period displayed on the graph (e.g., "Last 7 Days").
        *   Visually inspect the graph:
            *   Are the axes labeled appropriately (Date/Time on the X-axis, User Count on the Y-axis)?
            *   Is the graph clearly rendered (lines are smooth, data points are visible)?
    4.  **Data Point Verification:**
        *   For at least 3 distinct data points on the graph, note the date/time and the corresponding User Count value displayed on the graph.
        *   Compare these values to the historical data gathered in Step 1.
    5.  **Time Period Filtering:**
        *   If the dashboard offers time period filtering (e.g., "Last 30 Days," "Last Quarter," "Custom Range"), select a different time period.
        *   Observe that the graph updates accordingly.
        *   Verify that the graph now displays the data for the newly selected time period.
        *   Repeat Step 4 (Data Point Verification) for this new time period, comparing the graph data to the appropriate historical data.
    6.  **Edge Case: No Data:**
        *   Select a time period where there is intentionally *no* user registration activity (e.g., a future date range).
        *   Verify that the graph displays appropriately to indicate "No Data Available" (this may be a blank graph, a specific "No Data" message, or a line at zero).

*   **Expected Result:**

    *   The trend graph should be rendered correctly with clearly labeled axes and visible data points.
    *   The User Count values displayed on the graph must accurately reflect the historical data for the corresponding date/time.
    *   Time period filtering should function correctly, updating the graph to display data for the selected time range.
    *   When no data is available for a selected time period, the graph should display an appropriate "No Data Available" indication.

*   **Priority:** Medium (While data accuracy is paramount, the usability and functionality of the trend graph are also important for understanding user growth over time. This test will allow us to find issues if the data is inaccurate, the labels are wrong or the values do not represent the data.)
