# Test Cases for T1.3 - Non-Functional Requirements

**Test Case 1: Performance Under Load (Stress Test)**

*   **Title:** Performance Degradation Under High User Load

*   **Description:** This test aims to verify that the system maintains acceptable performance (response times) even when subjected to a high number of concurrent users and transactions. It simulates a peak usage scenario to identify potential bottlenecks and ensure scalability. This test focuses on measuring response times, resource utilization (CPU, memory), and error rates under sustained high load.

*   **Steps:**

    1.  **Environment Setup:** Ensure the test environment closely mirrors the production environment (hardware specifications, network configuration, database configuration).
    2.  **Test Data Preparation:** Prepare a realistic dataset representing typical user activity. This should include a mix of common user actions (e.g., searching, viewing product details, adding to cart, checkout).
    3.  **Load Test Tool Configuration:** Configure a load testing tool (e.g., JMeter, LoadRunner, Gatling) to simulate a specific user load profile. Start with a baseline of 'X' concurrent users. Gradually increase the number of concurrent users in increments of 'Y' (e.g., 10, 20, 50 users) every 'Z' minutes (e.g., 2, 5, 10 minutes).
    4.  **Monitoring Setup:** Configure monitoring tools (e.g., New Relic, Datadog, Prometheus) to track key performance indicators (KPIs) during the test. These KPIs should include:
        *   Average Response Time for key transactions (e.g., homepage load, search, add to cart, checkout).
        *   Error Rate (e.g., HTTP 500 errors, database connection errors).
        *   CPU Utilization (application server(s), database server(s)).
        *   Memory Utilization (application server(s), database server(s)).
        *   Network Latency.
        *   Database Query Performance (execution time).
    5.  **Test Execution:** Execute the load test, gradually increasing the user load as defined in Step 3.  Run the test for a predetermined duration (e.g., 1 hour, 2 hours) to ensure sustained load.
    6.  **Data Collection:** Throughout the test, continuously collect data from the monitoring tools on the KPIs defined in Step 4.
    7.  **Analysis:** After the test, analyze the collected data to identify performance bottlenecks and areas where the system is struggling.

*   **Expected Result:**

    *   **Response Time Threshold:** Average response time for key transactions should remain below a predefined threshold (e.g., 3 seconds for homepage load, 5 seconds for search, 7 seconds for checkout) even at the peak user load.
    *   **Error Rate Threshold:** The error rate should remain below a predefined threshold (e.g., less than 1% of all requests) throughout the test.  No critical errors (e.g., database connection failures) should occur.
    *   **Resource Utilization:** CPU and memory utilization on the application and database servers should remain within acceptable limits (e.g., below 80% on average).  No resource exhaustion (e.g., memory leaks) should be observed.
    *   The system should not crash or become unresponsive under the applied load.
    *   System should be able to gracefully handle increased loads and then recover once the load decreases.

*   **Priority:** High
**Test Case 2: Security - Authentication Vulnerability**

*   **Title:** Authentication Bypass via Brute-Force Attack Prevention

*   **Description:** This test verifies the system's resistance to brute-force attacks on the authentication mechanism. It ensures that attackers cannot gain unauthorized access by repeatedly attempting different username/password combinations. This test focuses on confirming lockout mechanisms, rate limiting, and other security measures designed to mitigate brute-force attacks.

*   **Steps:**

    1.  **Account Setup:** Identify or create a test user account with known credentials.
    2.  **Brute-Force Attack Simulation:** Use a password cracking tool (e.g., Hydra, Burp Suite Intruder, OWASP ZAP) or a custom script to simulate a brute-force attack on the login endpoint. Configure the tool to attempt a large number of login attempts (e.g., 100, 500, 1000) with different password combinations over a short period (e.g., 5 minutes, 10 minutes).  Vary the password list used for the attack (e.g., common passwords, dictionary attacks, permutations).
    3.  **Lockout Verification:** After a predefined number of failed login attempts (e.g., 3, 5, 10), verify that the account is locked out.  The lockout mechanism should prevent further login attempts for a specific period.
    4.  **Lockout Duration:** Verify the duration of the lockout period. The lockout should last for a reasonable time (e.g., 15 minutes, 30 minutes, 1 hour) as specified in the security requirements.
    5.  **Lockout Messaging:** Verify that the user receives a clear and informative message indicating that their account has been locked out due to too many failed login attempts. The message should not provide any hints about the correct password or other sensitive information.
    6.  **Account Recovery:** Verify the account recovery process after a lockout.  Users should be able to regain access to their account through a secure password reset mechanism (e.g., email verification, security questions).
    7.  **Rate Limiting (Optional):**  If rate limiting is implemented at the IP address level, verify that subsequent login attempts from the same IP address are also blocked or throttled after a certain number of failed attempts.

*   **Expected Result:**

    *   **Account Lockout:** The test user account should be locked out after a predefined number of failed login attempts.
    *   **Lockout Duration Enforcement:** The lockout period should be enforced correctly and should match the configured duration.
    *   **Clear Error Messaging:** Users should receive a clear and informative error message indicating that their account is locked out and the reason for the lockout.
    *   **Successful Account Recovery:**  The account recovery process should function correctly, allowing the user to securely reset their password and regain access to their account.
    *   **No Unauthorized Access:**  The attacker should *not* be able to bypass the authentication mechanism and gain unauthorized access to the account, even after numerous failed login attempts.
    *   **Logging/Auditing:** Unsuccessful login attempts should be logged and audited for security monitoring purposes.

*   **Priority:** High
