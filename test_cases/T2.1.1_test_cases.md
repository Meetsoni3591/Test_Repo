# Test Cases for T2.1.1 - Basic Details Restaurant

Okay, here are two detailed test cases, covering different aspects of the "Basic Details Restaurant" task.  One focuses on successful creation and verification, the other focuses on an edge case/negative scenario.

**Test Case 1: Successful Restaurant Creation with Basic Details**

*   **Title:** Verify Restaurant Creation with Valid Basic Details

*   **Description:** This test case verifies that a user can successfully create a restaurant profile by providing valid input for name, address, phone number, logo, and venue type (bar, club, or lounge). This ensures the core functionality of adding a restaurant's basic details is working as expected.

*   **Steps:**

    1.  **Pre-condition:** User is logged in and has the appropriate permissions to create a restaurant profile. User is navigated to the "Add Restaurant" or "Create Restaurant Profile" page.
    2.  Enter a valid Restaurant Name (e.g., "The Spicy Spoon").  Ensure the name adheres to any character length or format constraints (e.g., alphanumeric characters, no special symbols).
    3.  Enter a valid Restaurant Address (e.g., "123 Main Street, Anytown, CA 91234").  Ensure the address fields allow for sufficient length.
    4.  Enter a valid Phone Number (e.g., "555-123-4567").  Confirm the phone number format is correct (e.g., US format with area code).
    5.  Upload a valid Logo image file (e.g., a .jpg or .png file).  Verify the file size is within the allowed limits, and the accepted file types are as expected.
    6.  Select "Bar" as the Venue Type from the dropdown list or radio button selection.
    7.  Click the "Save" or "Create" button to submit the restaurant details.

*   **Expected Result:**

    1.  The restaurant profile is successfully created without any error messages.
    2.  The user is redirected to the restaurant's profile page or a confirmation page.
    3.  On the restaurant profile page, the entered Restaurant Name, Address, Phone Number, and uploaded Logo are displayed correctly and in the expected format.
    4.  The Venue Type displayed on the profile page or in the restaurant listing shows "Bar".
    5.  The restaurant is now visible in the relevant search results or restaurant listings (if applicable).
    6.  Data is correctly stored in the database. The name, address, phone number, logo path, and venue type are stored in the appropriate database fields.

*   **Priority:** High

**Test Case 2: Restaurant Creation with Invalid Phone Number**

*   **Title:** Verify Error Handling for Invalid Phone Number Format

*   **Description:** This test case verifies that the application correctly handles invalid phone number formats during restaurant creation. This ensures data integrity and prevents incorrect data from being stored.

*   **Steps:**

    1.  **Pre-condition:** User is logged in and has the appropriate permissions to create a restaurant profile. User is navigated to the "Add Restaurant" or "Create Restaurant Profile" page.
    2.  Enter a valid Restaurant Name (e.g., "The Spicy Spoon").
    3.  Enter a valid Restaurant Address (e.g., "123 Main Street, Anytown, CA 91234").
    4.  Enter an invalid Phone Number (e.g., "123-456").  This number is too short.
    5.  Upload a valid Logo image file (e.g., a .jpg or .png file).
    6.  Select "Club" as the Venue Type from the dropdown list or radio button selection.
    7.  Click the "Save" or "Create" button to submit the restaurant details.

*   **Expected Result:**

    1.  The restaurant profile creation fails.
    2.  An appropriate error message is displayed to the user, clearly indicating that the phone number is invalid and specifying the expected format (e.g., "Invalid phone number format. Please enter a valid phone number in the format XXX-XXX-XXXX."). The error message should be user-friendly and informative.
    3.  The error message should be displayed near the phone number field.
    4.  The application should *not* proceed to create the restaurant profile with the invalid phone number.
    5.  The other input fields (Restaurant Name, Address, Logo, Venue Type) should be retained so that the user doesn't have to re-enter them after correcting the phone number.  This improves the user experience.
    6.  The invalid phone number is *not* stored in the database.

*   **Priority:** High
