# Test Cases for T2.1.4 - Venue Status Management Restaurant

Okay, here are two detailed test cases covering the "Venue Status Management - Restaurant: Manage Signed/Not Signed Status" feature, written from the perspective of a senior QA engineer:

**Test Case 1: Valid Transition from "Not Signed" to "Signed" Status**

*   **Title:** Verify Successful Transition from "Not Signed" to "Signed" Status with Valid Data

*   **Description:** This test case verifies that a restaurant venue's status can be successfully updated from "Not Signed" to "Signed" via the administrative interface, and that the change is reflected correctly in the system. This test ensures the basic functionality of status updating is working as expected.

*   **Steps:**

    1.  **Pre-condition:** Log in to the administrative interface with valid credentials having sufficient privileges to modify venue status.
    2.  Navigate to the Venue Management section.
    3.  Search for a specific restaurant venue that currently has the status "Not Signed". Record the venue ID or name for later verification.
    4.  Select the "Edit" or "Update" option for the selected restaurant venue.
    5.  Locate the "Status" field or dropdown menu within the venue editing form.
    6.  Select "Signed" from the available status options.
    7.  If applicable, fill in any required fields when transitioning to "Signed" status (e.g., Date Signed, Contract ID, User who signed). Use valid data formats for each field.
    8.  Save the changes made to the venue details.
    9.  Navigate back to the Venue Management section and search for the same restaurant venue from step 3.

*   **Expected Result:**

    1.  The system displays a success message confirming the status update (e.g., "Venue status updated successfully").
    2.  The selected restaurant venue's status is now displayed as "Signed" in the Venue Management table.
    3.  The database record for the venue is updated with the "Signed" status and any related fields (e.g., Date Signed, Contract ID, User who signed) are populated correctly and match the entered data.
    4.  Any related reporting metrics (e.g., number of signed venues) are updated to reflect the change.
    5.  Audit logs reflect the change, including the user who made the change and the timestamp of the change.

*   **Priority:** High

**Test Case 2: Attempt Transition from "Signed" to "Not Signed" Status with missing data**

*   **Title:** Verify Error Handling during Transition from "Signed" to "Not Signed" Status with missing data.

*   **Description:** This test case verifies the system's ability to handle invalid data when attempting to transition a restaurant venue's status from "Signed" to "Not Signed."

*   **Steps:**

    1.  **Pre-condition:** Log in to the administrative interface with valid credentials having sufficient privileges to modify venue status.
    2.  Navigate to the Venue Management section.
    3.  Search for a specific restaurant venue that currently has the status "Signed". Record the venue ID or name for later verification.
    4.  Select the "Edit" or "Update" option for the selected restaurant venue.
    5.  Locate the "Status" field or dropdown menu within the venue editing form.
    6.  Select "Not Signed" from the available status options.
    7.  Attempt to save the changes without filling in the required "Reason for Unsigning".

*   **Expected Result:**

    1.  The system displays an error message indicating that required fields for the transition are missing (e.g., "Reason for Unsigning is required").
    2.  The status change is not saved, and the restaurant venue remains in the "Signed" status.
    3.  The error message is clear, user-friendly, and provides specific information about which fields are missing or invalid.
    4.  The database record for the venue remains unchanged.
    5.  Audit logs reflect the attempted change and the reason for failure.

*   **Priority:** High
