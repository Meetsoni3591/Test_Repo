# Test Cases for T7.3 - Support Staff Role

Okay, here are two detailed test cases based on the provided task "Support Staff Role: Access to user profiles for support queries," designed to verify the proper functionality and security of this feature.

**Test Case 1:  Support Staff - View User Profile Details**

*   **Title:**  Verify Support Staff Can View User Profile Details for Support Purposes

*   **Description:** This test case validates that users with the "Support Staff" role can access and view the necessary information within a user profile to effectively address support queries, while also verifying they cannot access sensitive or administrative-only information.

*   **Steps:**

    1.  **Login:** Log into the application as a user with the "Support Staff" role.  Use valid credentials for a designated Support Staff test account.
    2.  **Navigate:**  Navigate to the user management or user search section of the application (e.g., a section labeled "Users," "Manage Accounts," or similar).  The exact navigation path will depend on the application's structure.
    3.  **Search:** Search for a specific user account (e.g., by username, email address, or user ID).  Use a valid, non-admin user account for this search.
    4.  **Select User:** Select the target user account from the search results to view their profile details.
    5.  **Verify Profile Details:**  Carefully examine the displayed user profile information. Verify the following:
        *   **Visible Fields:** The following information is visible and correctly populated:
            *   Username
            *   Email address
            *   Account creation date
            *   Last login date
            *   Account status (e.g., Active, Inactive, Suspended)
            *   Contact information (if available and relevant)
            *   User's subscriptions or purchased products (if applicable).
            *   User's support ticket history (if applicable).
        *   **Hidden/Read-Only Fields:**  The following information is *NOT* visible or is displayed as read-only for the Support Staff user:
            *   User's password (even masked)
            *   User's payment information (e.g., credit card details)
            *   Administrative privileges or role assignments
            *   Internal application settings specific to the user account
            *   Any data considered highly sensitive or personally identifiable information (PII) beyond what's needed for basic support.
    6.  **Attempt Modification (If Possible):** If the UI allows, attempt to modify any of the displayed user profile fields.  Try to save the changes.

*   **Expected Result:**

    *   **Step 5 (Visible Fields):**  All specified visible user profile details are displayed correctly and are relevant to providing support.  The information is accurate and corresponds to the user account being viewed.
    *   **Step 5 (Hidden/Read-Only Fields):**  Sensitive or administrative information is either completely hidden from the Support Staff user or is displayed as read-only (i.e., cannot be edited).  An appropriate message or indication should be shown if modification is attempted on read-only fields.
    *   **Step 6 (Attempt Modification):**  Any attempt to modify restricted fields (even if displayed) should fail, and the application should display an appropriate error message indicating insufficient permissions or that the field is read-only. The profile changes should not save.

*   **Priority:** High

**Test Case 2:  Support Staff - Failed Access Attempts**

*   **Title:**  Verify Support Staff Cannot Access Admin User Profiles or Functionality

*   **Description:** This test case ensures that Support Staff users are prevented from accessing profiles of users with higher privileges (e.g., Administrator accounts) and also confirms that they cannot access any administrator-level functionality through user profile access. This is crucial for maintaining data security and preventing unauthorized actions.

*   **Steps:**

    1.  **Login:** Log into the application as a user with the "Support Staff" role. Use valid credentials for a designated Support Staff test account.
    2.  **Navigate:** Navigate to the user management or user search section of the application (e.g., a section labeled "Users," "Manage Accounts," or similar).
    3.  **Search for Admin:** Search for a user account that has "Administrator" privileges or a similar high-level role. Use the username, email or ID of a specific admin user for this search.
    4.  **Select Admin User:** Attempt to select the Administrator user account from the search results to view their profile details.
    5.  **Attempt Admin Functions:** If access to the admin profile is *somehow* granted (which is NOT expected), attempt to perform administrative actions from within the admin user profile, such as:
        *   Changing the admin user's role.
        *   Resetting the admin user's password.
        *   Deleting the admin user account.
        *   Accessing system logs or audit trails.
    6.  **Direct URL Access (Negative test):** If it's possible to directly access user profiles via a URL (e.g., `https://example.com/users/profile/123`), attempt to access the admin user profile directly by modifying the URL with the ID of the Administrator user.

*   **Expected Result:**

    *   **Step 4 (Select Admin User):** Access to the Administrator user's profile should be explicitly denied. The application should display an appropriate error message such as "Insufficient Permissions," "Access Denied," or "User not found" (if you don't want them to know the admin user exists).  Ideally, the Admin user profile should not even be listed in the search results for Support Staff.
    *   **Step 5 (Attempt Admin Functions):** If, against expectations, an admin profile is somehow accessed, all attempts to perform administrative actions should fail, and clear error messages should be displayed.  No changes should be applied to the admin user account.
    *   **Step 6 (Direct URL Access):** Accessing the admin user profile via a direct URL should also be denied with an appropriate error message.

*   **Priority:** Critical
