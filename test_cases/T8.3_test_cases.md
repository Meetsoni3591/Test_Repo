# Test Cases for T8.3 - Automated Workflows & Alerts

Okay, here are two detailed test cases based on the provided task "Automated Workflows & Alerts: Implement Venue Contract Renewal reminders, User Re-Engagement campaigns," written from the perspective of a Senior QA Engineer.  These tests are designed to verify the core functionality of the implemented workflows.

**Test Case 1: Venue Contract Renewal Reminder Workflow - Successful Contract Renewal**

*   **Title:** Verify Venue Contract Renewal Reminder Workflow - Successful Renewal

*   **Description:** This test case verifies that the automated workflow for Venue Contract Renewal Reminders functions correctly when a venue contract is successfully renewed within the reminder period.  It ensures the appropriate reminders are triggered, and crucially, that the workflow stops correctly upon renewal, preventing unnecessary further reminders.

*   **Steps:**

    1.  **Pre-condition:** Create a Venue record in the system. Set the `Contract Expiration Date` to be exactly 60 days from the current date.
    2.  **Pre-condition:** Verify that the Venue record is configured to receive Contract Renewal Reminders (e.g., a flag is set to `true` or the venue is subscribed to the correct notification type).
    3.  **Time Progression:** Allow the system to progress naturally to 30 days before the `Contract Expiration Date`.
    4.  **Monitor:** Check the Venue record's associated notification history (or related logging mechanism) to confirm that the first reminder email was sent to the Venue Contact Person (e.g., check email logs, notification queue, or database). Verify that the email content matches the expected template for the first reminder (e.g., mentions 30 days remaining, renewal instructions, etc.).
    5.  **Time Progression:** Allow the system to progress naturally to 15 days before the `Contract Expiration Date`.
    6.  **Monitor:** Check the Venue record's associated notification history (or related logging mechanism) to confirm that the second reminder email was sent. Verify the email content matches the expected template for the second reminder (e.g., mentions 15 days remaining, potential late fees if not renewed, etc.).
    7.  **Action:**  Within the 15-day window, simulate a successful contract renewal. This could involve updating the `Contract Expiration Date` to a date in the future (e.g., one year from the original expiration date), setting a `Contract Renewal Status` to `Renewed`, or any other system-defined flag indicating successful renewal.
    8.  **Time Progression:** Allow the system to progress beyond the original `Contract Expiration Date` by a period of, for example, 10 days.
    9.  **Monitor:** Check the Venue record's associated notification history.  Ensure *no* further reminder emails were sent *after* the contract renewal was marked as successful.
    10. **Validate Data:** Check the system logs (if available) to ensure that the workflow process recognized the renewal and terminated correctly.

*   **Expected Result:**

    *   The first reminder email is successfully sent 30 days before the `Contract Expiration Date` with the correct content.
    *   The second reminder email is successfully sent 15 days before the `Contract Expiration Date` with the correct content.
    *   *No* further reminder emails are sent after the contract renewal is marked as successful, even if the system continues to run past the original `Contract Expiration Date`.
    *   System logs (if accessible) indicate that the workflow process recognized the renewal and terminated appropriately.
    *   The data within the system accurately reflects that the contract has been renewed (e.g., updated `Contract Expiration Date`, `Contract Renewal Status`).

*   **Priority:** High - This test covers the core, intended functionality of the contract renewal reminder workflow. Failure here indicates a significant defect.

**Test Case 2: User Re-Engagement Campaign - User Engagement after Email Interaction**

*   **Title:** Verify User Re-Engagement Campaign - Successful User Engagement

*   **Description:** This test case verifies the User Re-Engagement campaign functions correctly by sending a re-engagement email to a user who hasn't interacted with the platform for a specified period and confirms the system correctly stops the re-engagement workflow when the user engages with the platform after receiving the re-engagement email.

*   **Steps:**

    1.  **Pre-condition:** Create a User record in the system and ensure the User hasn't logged in or performed any key actions (e.g., creating content, making a purchase) for a period exceeding the defined "inactivity" threshold for the re-engagement campaign (e.g., 60 days). Ensure the user is opted-in to receive email communications.
    2.  **Time Progression:** Allow the system to progress naturally until the User meets the inactivity criteria for the re-engagement campaign (e.g., 60 days of inactivity since last login/action).
    3.  **Monitor:** Verify that the re-engagement email is successfully sent to the User. Check email logs or notification queues to confirm the email was sent and verify the email content matches the expected template (e.g., includes a compelling offer, a call to action to return to the platform).
    4.  **Action:** After the User receives the re-engagement email, simulate a "re-engagement" action within a defined time window (e.g., within 7 days). This action could be a login to the platform, clicking a link in the email, making a purchase, or any other action defined as "engagement" by the re-engagement campaign logic.
    5.  **Time Progression:** Allow the system to progress beyond the time the user took the engagement action.
    6.  **Monitor:** Check the User record's associated notification history (or logging mechanism) to ensure that no further re-engagement emails are sent to the User after the simulated engagement action.
    7.  **Validate Data:** Check system logs (if available) to ensure that the workflow process recognized the engagement and terminated correctly. Check data tracking within the system (e.g., last login date, last activity date) to ensure it reflects the user's re-engagement.

*   **Expected Result:**

    *   The re-engagement email is successfully sent to the inactive User after the specified inactivity period with the correct content.
    *   *No* further re-engagement emails are sent to the User after the User performs the defined engagement action (e.g., logs in, clicks link) within the defined time window.
    *   System logs (if accessible) indicate that the workflow process recognized the user engagement and terminated the campaign appropriately.
    *   The User's data within the system is updated to reflect the re-engagement activity (e.g., updated last login date, updated last activity date).

*   **Priority:** High - This tests the fundamental functionality of the re-engagement campaign, verifying it correctly identifies inactive users, sends re-engagement emails, and stops sending emails when users re-engage. Failure here would render the campaign ineffective.

These test cases are a good starting point, but further tests should be added to cover edge cases, error handling, and other potential failure points.  For example, testing error handling if an email fails to send, or testing the workflow's behavior when dealing with a large number of users.  Also, performance and scalability tests should be considered.
