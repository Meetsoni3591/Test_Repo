# Test Cases for T8.4 - Security & Compliance

Okay, here are two detailed test cases based on the provided task, focusing on different aspects of the "Security & Compliance" requirements: Data Encryption and Audit Logs.

**Test Case 1: Data Encryption Validation - REST API**

*   **Title:** Verify Data Encryption at Rest for Sensitive Customer Data via API
*   **Description:** This test case verifies that sensitive customer data stored in the database is encrypted at rest, and that this encryption is correctly applied when accessing the data through the REST API. This test specifically focuses on verifying the encrypted data isn't readable without proper authentication and authorization.
*   **Steps:**
    1.  **Pre-requisite:** Ensure the Data Encryption feature is enabled in the application's configuration. Have a test customer account with sensitive data (e.g., credit card information, social security number, address) ready.
    2.  **Login & Create Data:** Log in to the application with appropriate credentials (e.g., administrator or a user with create data permissions) via the API.
    3.  **API Call to Create Customer Data:** Using a POST request to the relevant REST API endpoint (e.g., `/api/customers`), create a new customer record including sensitive data in the request body.  Record the customer ID generated by the API. Use different data types for the sensitive fields to ensure all fields are encrypted correctly (e.g., string, number, date).
    4.  **Direct Database Access (Out of Scope):** (Optional for verification/troubleshooting) Access the database directly (using appropriate credentials and tools) and locate the newly created customer record using the customer ID. Verify that the sensitive data fields in the database are encrypted and are not human-readable.
    5.  **API Call to Retrieve Customer Data:** Using a GET request to the relevant REST API endpoint (e.g., `/api/customers/{customerID}`), retrieve the newly created customer record using the customer ID.
    6.  **Validate Decryption:** Analyze the API response. Verify that the sensitive data fields in the response body are correctly decrypted and displayed in their original, human-readable format.
    7.  **Tamper Data Test:** Create API call to Update Customer Data with valid admin authorization and tamper the encrypted sensitive data.
    8.  **Validate Tampered data:** Analyze the API response. Verify that the sensitive data fields cannot be tampered with and the API returns an error message.

*   **Expected Result:**
    *   Sensitive data provided during creation via the API should be successfully stored in the database in an encrypted format (verified by direct database access, if performed).
    *   When retrieving the customer record via the API, the sensitive data should be correctly decrypted and displayed in its original, human-readable format in the API response.
    *   The application should not allow access to or modification of the encrypted data without proper authentication and authorization. Unauthorized access attempts should result in appropriate error messages (e.g., 401 Unauthorized, 403 Forbidden).
    *   Attempting to update sensitive fields with invalid/tampered data should result in a clear error response from the API, indicating the data integrity violation.
*   **Priority:** High
*   **Environment:** Test/Staging
*   **Dependencies:** Data Encryption feature must be configured, API endpoints must be stable, Database access available (if doing direct validation).

**Test Case 2: Audit Log Functionality - User Authentication**

*   **Title:** Verify Audit Log Generation for User Authentication Events
*   **Description:** This test case verifies that the application correctly generates audit logs for user authentication events (login, logout, failed login attempts). These logs are crucial for security monitoring, incident investigation, and compliance requirements.
*   **Steps:**
    1.  **Pre-requisite:** Audit logging feature must be enabled and configured to log authentication events. Ensure the location and format of audit logs are known (e.g., file path, database table, format).
    2.  **Successful Login:** Log in to the application with valid credentials.
    3.  **Failed Login:** Attempt to log in with invalid credentials multiple times (e.g., incorrect password).
    4.  **Logout:** Log out of the application.
    5.  **Inspect Audit Logs:** Access and inspect the audit logs (file or database) using appropriate tools.
    6.  **Validate Entry Details:** Verify that the audit logs contain entries for the following events:
        *   Successful login
        *   Failed login attempts (at least one entry for each attempt)
        *   Logout
    7.  **Verify Log Content:** For each log entry, verify the following information is accurately recorded:
        *   Timestamp of the event
        *   Username of the user attempting to authenticate (or the attempted username for failed logins)
        *   Source IP address of the user (if available)
        *   Type of event (e.g., "Login Success", "Login Failure", "Logout")
        *   Result of the event (e.g., "Success", "Failure")
        *   Any other relevant information, such as session ID or authentication method used.
    8.  **Tamper Data Test:** Attempt to manually modify/delete entries in the audit logs (directly in the file/database).

*   **Expected Result:**
    *   Audit logs should contain accurate and complete entries for all user authentication events (login, logout, failed attempts).
    *   Each log entry should contain all the required information (timestamp, username, IP address, event type, result, etc.).
    *   The audit logs should be tamper-proof.  Attempts to modify or delete log entries directly should be detected or prevented (e.g., through file permissions, database constraints, or integrity checks).  Tampering should generate a separate log entry or alert.
    *   Audit logs should be stored in a secure location with appropriate access controls.
*   **Priority:** High
*   **Environment:** Test/Staging
*   **Dependencies:** Audit logging feature must be enabled and properly configured, access to audit logs must be available, ability to simulate failed login attempts.
*   **Note:** Consider rotating log files on a scheduled basis (daily, weekly, etc.) to minimize storage space and facilitate archiving. Ensure the log rotation process is also tested.
