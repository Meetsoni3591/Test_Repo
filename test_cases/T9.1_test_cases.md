# Test Cases for T9.1 - Growth KPIs

Okay, I'll create two detailed test cases covering different aspects of tracking the Growth KPIs mentioned in the task. These test cases will focus on verifying the accuracy of data displayed for specific KPIs.

**Test Case 1: Verification of Weekly/Monthly Active Users (WAU/MAU) Data**

*   **Title:** Verify WAU/MAU Calculation and Display Accuracy

*   **Description:** This test case verifies the accuracy of the Weekly and Monthly Active Users (WAU/MAU) data displayed on the Growth KPIs dashboard.  It ensures that the system correctly identifies and counts active users based on defined criteria (e.g., logged-in, performed a specific action) within the specified timeframes.

*   **Steps:**

    1.  **Data Setup:**
        *   Ensure a test environment contains a sufficient number of users (e.g., > 1000) registered in the system.
        *   Create a controlled scenario where a specific subset of users (e.g., 100 users for WAU, 250 users for MAU) are marked as "active" by performing a specific action (e.g., logging in, creating an event, booking a venue) within the current week and month.
        *   Ensure another subset of users remains inactive (no activity within the current week/month).
        *   Verify that the active users are genuinely active, and the inactive users are genuinely inactive.
    2.  **Navigation:** Navigate to the Growth KPIs dashboard or the section where WAU/MAU data is displayed.
    3.  **Data Retrieval:** Note down the displayed WAU and MAU values for the current week and month.
    4.  **Manual Calculation:**
        *   Using direct database queries or backend logs (depending on access), manually calculate the actual WAU and MAU based on the "active" user criteria defined by the business requirements.  For example, if "active" is defined as "logged in within the last week/month", query the login logs for distinct users within those periods.
        *   Document the manual calculation method and results for auditability.
    5.  **Comparison:** Compare the displayed WAU/MAU values (Step 3) with the manually calculated WAU/MAU values (Step 4).
    6.  **Date Range Validation (Boundary Test):**
        *   Change the date range on the dashboard to view the WAU/MAU for the last few weeks or months.
        *   Repeat steps 3-5 for these date ranges to ensure historical data is also accurate.
    7.  **Edge Case Validation:**
        *   Check WAU/MAU for a week/month with no active users.
        *   Check WAU/MAU for a week/month with all users active.
        *   Check that deactivated/blocked users are not counted in WAU/MAU.

*   **Expected Result:**

    *   The displayed WAU and MAU values on the Growth KPIs dashboard must precisely match the manually calculated WAU and MAU values for all tested date ranges and scenarios.
    *   WAU and MAU should be displayed as 0 for time periods where no users are considered active.
    *   WAU and MAU should correctly reflect deactivated and blocked users by not counting them.
    *   No performance issues should be noticed in the process.

*   **Priority:** High (Core metric; inaccuracies directly impact business decisions)

**Test Case 2: Verification of Member Conversion Rate Data**

*   **Title:** Verify Member Conversion Rate Calculation and Display Accuracy

*   **Description:** This test case verifies that the Member Conversion Rate (the percentage of users who convert from a free or trial account to a paid membership) is calculated and displayed correctly on the Growth KPIs dashboard. It covers different conversion scenarios and time periods.

*   **Steps:**

    1.  **Data Setup:**
        *   Ensure the test environment contains a sufficient number of free/trial and paid users.
        *   Create specific conversion scenarios:
            *   Convert a defined number of free users to paid users within the current week/month.
            *   Ensure some users remain in the free/trial tier.
            *   Ensure some users are already in the paid tier at the start of the week/month.
            *   Ensure some users are newly created and then immediately converted.
            *   Ensure some users are downgraded from a paid tier back to a free/trial tier.
        *   Verify that user statuses accurately reflect their tiers (free, trial, paid) in the database.
    2.  **Define Conversion Criteria:** Clarify (with stakeholders) the specific criteria for conversion to be considered in the calculation of the conversion rate. For example, does it include upgrades within paid tiers, or only free-to-paid conversions? Document this criteria.
    3.  **Navigation:** Navigate to the Growth KPIs dashboard or the section displaying the Member Conversion Rate.
    4.  **Data Retrieval:** Note down the displayed Member Conversion Rate value for the current week/month.
    5.  **Manual Calculation:**
        *   Using database queries, manually calculate the Member Conversion Rate based on the conversion criteria (Step 2). The formula is typically: `(Number of New Paid Users During the Period) / (Total Number of Free/Trial Users at the Start of the Period) * 100`
        *   Account for users who downgraded and newly created users.
        *   Document the manual calculation method and results.
    6.  **Comparison:** Compare the displayed Member Conversion Rate value (Step 4) with the manually calculated Member Conversion Rate value (Step 5).
    7.  **Date Range Validation (Boundary Test):**
        *   Change the date range on the dashboard to view the conversion rate for the last few weeks or months.
        *   Repeat steps 3-6 for these date ranges to verify historical accuracy.
    8.  **Edge Case Validation:**
        *   Check the conversion rate when there are no free users.
        *   Check the conversion rate when all free users convert.
        *   Check the conversion rate for a period with no new users.
    9.  **Currency Validation:**
        *   If the conversion also involves a financial transaction, verify that the currency used in the transaction is correct and consistent with the user's location or preferences.

*   **Expected Result:**

    *   The displayed Member Conversion Rate value on the Growth KPIs dashboard must precisely match the manually calculated Member Conversion Rate value, considering the defined conversion criteria, for all tested date ranges and scenarios.
    *   The conversion rate should be displayed as 0% when there are no eligible conversions or no free/trial users.
    *   Conversion rate calculations should be accurate even when users downgrade or new users are immediately converted.
    *   Currency consistency should be verified.

*   **Priority:** High (Key indicator of user engagement and revenue generation)

These test cases are designed to be thorough and cover various scenarios. Remember to adapt them to your specific system's implementation and business logic. Good luck!
